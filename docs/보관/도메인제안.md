# 새 도메인 적용 제안 - IoT 센서 온도 예측

> 작성일: 2026-09-30 · 상태: **제안 (검증 전)**

## 결론

HAIC 실습(서빙 → MLOps → AIOps)을 새 도메인에 적용한다면 **IoT 센서 온도 예측**을 제안합니다. 대상은 **데이터센터 서버실**입니다.

차별점은 도메인이 아니라 운영 질문입니다.

> **"오차가 커졌다고 무조건 재학습해도 되는가? - 센서 고장을 드리프트로 착각하면 고장 데이터로 재학습한다."**

기존 파이프라인에 **데이터 검증** 단계를 서빙 입력과 재학습 직전 두 곳에 추가하고, 센서 고장과 실제 드리프트를 구분하는 실습으로 만듭니다.
목표는 **"고장 데이터로는 예측도, 재학습도 하지 않는다"** 입니다.

## 도메인 매핑표 (과제 양식 7장)

B2B 관점: **데이터센터(IDC) 운영사의 시설 운영팀**에게 "서버실 과열을 미리 알고, 센서 고장에 속지 않는 온도 예측"을 제공합니다.

| 템플릿 개념 (HAIC) | 예시: 프랜차이즈 수요 예측 | **우리 팀 아이디어: 서버실 온도 예측** |
|------|------|------|
| 예측 대상: 다음날 종가 | 다음날 매장별 판매량 | **1시간 뒤 서버실(랙 흡기) 온도 (°C)** |
| 입력 시퀀스: 최근 20거래일 (close, volume) | 최근 28일 (판매량, 프로모션 여부) | **최근 24시간 (온도, IT 전력 부하 kW)** - 서버 부하가 곧 발열원이라 습도보다 설명력이 큼 |
| 데이터 공급: 대시보드 CSV 업로드 | POS 일마감 데이터 업로드 | **시설 관리 시스템(BMS/DCIM) 센서 로그를 1시간 단위로 집계한 CSV 업로드** |
| 배포 게이트: RMSE ≤ $4.00 | MAPE ≤ 15% (발주 오차 허용 범위) | **RMSE ≤ 1.0°C (잠정)** - 권장 흡기 온도 대역(18~27°C) 안에서 냉방 조정 판단에 쓸 수 있는 오차. 기준 모델 RMSE를 보고 확정 |
| 드리프트 신호: 변동성 3배 급변 | 신메뉴 출시, 휴가철, 경쟁점 오픈 | **진짜 드리프트:** 냉방 설정온도 상향 정책(PUE 개선, 22°C → 25°C), 서버 증설(부하가 한 단계 올라 유지)<br>**가짜 드리프트(⭐ 차별점):** 센서 고장(0 고정, 값 튐, 결측) → 재학습하면 안 됨<br>※ 냉방기 고장은 드리프트가 아니라 **장애** (재학습 대상 아님, 5장 참고) |
| 재학습: 최근 21거래일 fine-tuning | 최근 4주 데이터로 fine-tuning | **최근 7일(168시간) fine-tuning, 단 데이터 검증을 통과한 경우에만** |
| 알림: aiops.log [WARN] | 본사 SCM 담당자 메신저 알림 | **진짜 드리프트:** `[WARN]` → 시설 운영팀(냉방 설정 점검)<br>**센서 고장:** `[SKIP] sensor fault` → 설비 유지보수팀(센서 교체 요청) |
| 이해관계자: 투자 분석가, 운영자 | 점주(재고 폐기), 본사 SCM(발주), 경영진(손실) | **시설 운영팀**(과열 대응 지연) · **IDC 고객사**(과열로 서버 장애, SLA 위반) · **설비 유지보수팀**(센서 교체) · **경영진**(과냉방 전력비, 전력 효율 지표 PUE 악화) |

## 1. 배경 - 왜 도메인만 바꾸면 안 되는가

- 전력 수요, 주가, 판매량 예측 같은 주제는 이미 흔합니다. 데이터만 바꾸면 "같은 실습에 다른 CSV"가 됩니다.
- 현재 Day3 파이프라인은 아래 가정 위에 서 있습니다. **도메인마다 이 중 무엇이 깨지는지**가 곧 그 도메인만의 운영 문제이고, 차별점입니다.

| # | 현재 코드의 가정 | 코드 위치 |
|---|------|------|
| A | 실제값(정답)이 곧바로 들어온다 | `routers/predict.py` `batch_test()` |
| B | 오차가 커지면 모델이 낡은 것이다 | `monitoring/drift_detector.py` `is_drift()` |
| C | 최근 데이터로 학습하면 미래에도 잘 맞는다 | `monitoring/retrain_trigger.py` (최근 21일로 재학습) |
| D | 모든 상황을 모델 하나로 처리한다 | `models:/HAIC_Predictor/Production` |

IoT 센서 온도 예측은 **가정 B**를 깨뜨립니다. 오차가 커진 원인이 모델이 아니라 **데이터(센서)** 일 수 있습니다.

## 2. 선정 기준 - "전제가 확실히 성립하는가"

실습의 핵심 장면이 **학습 결과(가중치가 얼마나 바뀌는지 등)에 좌우되면**, 만들어 놓고도 재현되지 않을 수 있습니다.
그래서 **핵심 장면이 파이프라인 로직만으로 결정되는 도메인**을 골랐습니다.

## 3. 후보 비교

| 도메인 | 운영 질문 | 전제 확실성 | 판단 |
|------|------|:---:|------|
| 전력 수요 | (특별한 운영 질문 없음) | - | ❌ 흔한 주제, 차별점 없음 |
| 태양광 발전량 | 일시적 변화(오염·적설)에도 재학습하는가? | 낮음 | ❌ "재학습 후 악화" 장면이 학습 결과에 달려 있음. 밤 시간(발전량 0)이 RMSE를 희석함. 게이트가 같은 기간 데이터로 채점해 문제를 못 잡음 |
| 전기차 충전 수요 | 서서히 오르는 오차를 어떻게 잡는가? | 중간 | △ 추세 감지 통계가 새로 필요하고 공개 데이터가 부족함 |
| 배달 소요시간 | 날씨별로 모델을 나눠야 하는가? | 중간 | △ 여러 모델 라우팅으로 구조 변경이 큼 |
| LLM 서비스 응답 지연 | 배포가 원인이면 롤백해야 하는가? | 확실 | △ 재학습해도 오차가 줄어 문제가 가려짐. 가상 데이터만 가능 |
| 사기 탐지 | 정답이 늦게 오면 어떻게 감지하는가? | 확실 | △ RMSE 기반 Day3를 전면 재설계해야 함 |
| **IoT 센서 온도** | **센서 고장을 드리프트로 착각하는가?** | **확실** | ✅ **채택** |

## 4. IoT 센서 온도 예측의 전제가 확실한 이유

1. 센서가 고장 나 값이 0으로 떨어지거나 갑자기 튀면, 학습 범위(예: 15~35°C)를 벗어난 입력이 들어옵니다. 예측 오차가 크게 벌어집니다.
2. 현재 `check_and_trigger()`는 **RMSE만 보고** 재학습하므로, 재학습이 **반드시** 실행됩니다. (단, 결측은 예외 - 아래 두 번째 박스)
3. 해결책인 데이터 검증도 **규칙 기반이라 결과가 항상 같습니다.**
4. 따라서 **가상 데이터로도 전제가 성립합니다.**

> **⚠️ 전제 보완 (코드 검토 결과)**
> `retrain_trigger.py`는 재학습할 때 **시뮬레이션으로 보낸 배치가 아니라 마지막에 업로드된 CSV**를 사용합니다.
>
> ```python
> rows = load_rows(latest_upload())[-(21 + SEQ_LEN):]   # 배치 데이터가 아님
> ```
>
> 그래서 고장 배치만 보내면 재학습은 실행되지만 **학습 데이터는 정상 CSV**입니다. "고장 데이터로 재학습"이 성립하지 않습니다.
>
> **해결 (서버 코드 변경 없음):** `simulate_drift.py`가 고장 데이터를 기존 `/data/upload`로 **먼저 업로드한 뒤** 배치를 보냅니다.
> 그러면 `latest_upload()`가 고장 파일을 가리켜 전제가 성립하고, "새 센서 데이터가 들어왔다"는 실제 흐름과도 맞습니다.
> 참고로 기존 HAIC 실습에도 같은 불일치가 있습니다(감지는 가상 배치, 재학습은 업로드된 CSV).

> **⚠️ 결측 경로 (현재 코드로 확인함, 2026-09-30)**
>
> | 단계 | 동작 |
> |------|------|
> | 클라이언트 → 서버 | 표준 JSON에는 NaN이 없음. `requests`(2.33.1)는 NaN이 든 요청을 `InvalidJSONError`로 **거부**하고, 브라우저는 `null`로 보냄 (2026-09-30 구현 중 확인 - 처음에 "requests가 NaN을 그대로 전송"이라고 쓴 것은 오류) |
> | `null`이 도착하면 | 예측 계산 중 `TypeError` → **500 오류**, 로그 없음 (체크포인트 B에서 확인) |
> | 비표준 `NaN` 리터럴이 도착하면 | `BatchTestRequest`(pydantic)가 NaN을 **통과시킴** → 아래 두 줄 |
> | `compute_rmse()` → `is_drift()` | RMSE = `nan`, `nan > 기준값`은 항상 False → **드리프트를 조용히 놓침** (`[WARN]`도 `[SKIP]`도 없음) |
> | 응답 직렬화 | 예측값 NaN 때문에 `Out of range float values are not JSON compliant` → **500 오류** |
> | CSV 빈 칸 (`load_rows()`) | `float('')`에서 `ValueError` → 재학습 단계에서 **500 오류** |
>
> **결론:** 재학습 직전 검증만으로는 결측을 잡지 못합니다. **서빙 입력(배치)도 예측 전에 검증**해야 하고, `load_rows()`는 빈 칸을 오류 대신 NaN으로 읽어 검증 함수가 판정하게 해야 합니다.

## 5. 실습 설계

### 시나리오

| 시나리오 | 기존 규칙 (RMSE만 확인) | 새 규칙 (서빙 입력 + 재학습 전 데이터 검증) |
|------|------|------|
| ① 정상 | 재학습 없음 | 재학습 없음 |
| ② 센서 고장: 0 고정, 값 튐 | 엉터리 예측 → 드리프트 감지 → **고장 데이터로 재학습** ❌ | 입력 검증 실패 → **예측도 재학습도 하지 않음**, `[SKIP] sensor fault` ✅ |
| ② 센서 고장: 결측 | **드리프트를 놓치고 500 오류** ❌ (4장 두 번째 박스) | 입력 검증 실패 → `[SKIP] sensor fault` ✅ |
| ③ 진짜 드리프트: 설정온도 22→25°C, 서버 증설 | 재학습 ✅ | 검증 통과 → 재학습 ✅ |

**다루지 않는 것 - 냉방기 고장:** 과열은 새로운 정상 상태가 아니라 즉시 대응할 **장애**입니다. 이 데이터로 재학습하면 "과열이 정상"이라고 배운 모델이 배포되어, 센서 고장과 같은 문제가 생깁니다.
장애는 기존 설비 경보가 맡는다고 보고 **이번 범위에서 제외**합니다.
(계절 전환도 제외: 서버실은 항온 환경이라 외기 냉방을 쓰지 않는 한 효과가 약합니다.)

### 데이터 검증 규칙 (초안)

서빙 입력(배치)과 재학습 데이터(업로드 CSV)에 **같은 검증 함수**를 씁니다.

| 규칙 | 기준 (조정 가능) |
|------|------|
| 범위 이탈 | **10°C 미만이거나 40°C 초과** (서버실은 항온 환경. -10~50°C로 두면 0°C가 범위 안이라 "0 고정" 고장을 통과시킴) |
| 값 고정 | N시간 연속 같은 값 |
| 결측 | **NaN이 1개라도 있으면 실패** (NaN이 섞이면 RMSE 자체가 `nan`이 되어 무의미해지므로 허용 비율을 두지 않음) |
| 급변 | 1시간에 10°C 이상 변화 |

### 로그 흐름

```
정상:         (로그 없음)
센서 고장:     [SKIP] sensor fault (rule=out_of_range) - prediction & retrain blocked
진짜 드리프트:  [WARN] drift detected → [INFO] retrain triggered → [OK] new_rmse=... - production promoted
```

## 6. 이 실습으로 배울 수 있는 것

- **오차가 커진 원인은 두 가지다:** 모델이 낡은 경우와 데이터가 망가진 경우. 재학습 전에 데이터부터 의심해야 합니다.
- **자동화에는 안전장치가 필요하다:** 자동 재학습은 입력을 믿는 만큼만 안전합니다.
- **실무와 연결된다:** 실무 MLOps의 데이터 검증 도구(TFDV, Great Expectations)가 하는 역할을 직접 구현해 봅니다.
- **기존 실습 내용은 모두 유지된다:** Day1~3에서 배운 서빙, 레지스트리, 게이트, 캐시 무효화를 그대로 활용합니다.

## 7. 리스크 / 미확인 사항

| 항목 | 내용 | 영향 |
|------|------|------|
| 데이터 | 서버실 온도·IT 부하를 함께 공개한 데이터는 찾기 어려워 **가상 데이터로 확정** | 낮음 - 핵심 장면(②)은 로직으로 결정되어 가상 데이터로도 성립 |
| 고장 모델의 배포 여부 | 고장 데이터로 재학습한 모델이 **게이트까지 통과하는지**는 학습 결과에 달려 있음 | 낮음 - 보너스 장면일 뿐, 핵심은 재학습 실행 여부 |
| 재학습 데이터 소스 | 재학습은 배치가 아니라 `latest_upload()`를 사용함. 고장 데이터를 먼저 업로드해야 전제가 성립 (4장 참고) | 해결됨 - 시뮬레이션 스크립트에서 처리 |
| 검증 규칙 기준값 | 범위, N시간 같은 기준은 데이터를 보고 조정해야 함 | 중간 - 너무 엄격하면 ③ 실제 변화까지 차단함 |
| 전체 검증 | 이 문서는 **설계 검토 결과이며, 결측 경로(4장) 외에는 아직 코드로 실행해 보지 않음** | - |
