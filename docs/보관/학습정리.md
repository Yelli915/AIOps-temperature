## 전체 그림 - 무엇을 만드는 프로젝트인가

가상 종목 HAIC의 **다음날 종가를 예측하는 LSTM 모델**을 하나의 FastAPI 서버 위에서 3단계로 발전시킵니다.

```
Day1 서빙          Day2 MLOps                         Day3 AIOps
─────────         ─────────────────────────          ───────────────────────────────────
로컬 .keras  →    학습 → MLflow 기록 → 게이트($4)  →   예측 오차 감시(RMSE) → 드리프트 감지
FastAPI 서빙       → Registry 등록 → Production 승격     → fine-tuning → 게이트 → 자동 재배포
                  → Docker로 재현
```

**핵심 메시지:** 모델은 "한 번 학습해서 배포하면 끝"이 아니라, **학습 → 배포 → 감시 → 재학습 → 재배포**의 루프로 운영된다.
이번 변경들(#2~#6)은 이 루프의 빈 칸을 하나씩 채운 것입니다.

```
simulate_drift.py ──POST──▶ /predict/batch-test (batch_test)
   send_batch() #6              │ 슬라이딩 윈도우 예측 #4
                                ▼
                         recent_predictions (최근 21건)
                                │
                                ▼
                     check_and_trigger() #5 ──▶ is_drift() → compute_rmse() #3
                                │ 드리프트
                                ▼
                     fine_tune() → 게이트 통과 → Production 승격
                                │
                                ▼
                     _model_cache = None → 다음 요청에서 _load_from_mlflow() #2 로 새 버전 로드
```

## #1 `API_URL` 환경변수화

**목적**
README는 서버를 `8077`로 띄우고, Docker는 `8000`을 씁니다. 하드코딩된 `8000` 때문에 로컬 실습에서 연결이 거부되던 것을 해결.

**배울 수 있는 것**
- **환경별로 달라지는 값(주소·포트·경로)은 코드가 아니라 환경변수로** 받는다 → `os.getenv("API_URL", 기본값)`.
- 같은 코드를 로컬/컨테이너/운영에서 수정 없이 재사용하는 것이 배포 자동화의 기본 전제(12-Factor App의 "Config").
- 버그의 원인은 코드 로직이 아니라 **문서와 코드의 불일치**일 때도 많다.

## #2 `_load_from_mlflow()` - MLflow Production 모델 로드 (Day2)

**목적**
`MODEL_SOURCE=mlflow`일 때 로컬 `haic_v1.keras` 대신 **MLflow Model Registry에서 `Production` 단계로 승격된 모델**을 불러와 서빙.

**배울 수 있는 것**
- **Model Registry의 역할:** 서빙 코드는 "몇 번째 버전 파일"이 아니라 `models:/HAIC_Predictor/Production`이라는 **논리적 이름**만 안다. 어떤 버전을 서빙할지는 레지스트리에서 결정 → 학습 팀과 서빙 코드가 분리된다.
- **조립 블록 구조:** `main.py`, `train_and_register.py`는 그대로 두고 `model_loader.py` 한 함수만 바꿔 모델 소스를 교체. `LoadedModel` 래퍼가 local/mlflow를 **같은 인터페이스(`predict_one`)** 로 감싸기 때문에 가능.
- **스케일러는 고정:** 정규화 기준(`scaler.pkl`)이 바뀌면 그 기준으로 학습된 가중치와 어긋난다. 그래서 모델은 MLflow에서, 스케일러는 항상 같은 로컬 파일에서 로드한다 → **전처리도 모델의 일부**라는 감각.
- **Lazy vs Eager 로딩:** `get_model()`(첫 요청 때 로드 + 캐시) vs `load_eager()`(서버 시작 시 로드). 시작 속도와 첫 응답 지연의 트레이드오프.

## #3 `compute_rmse()` - RMSE 직접 구현 (Day3)

**목적**
최근 예측 기록의 오차를 하나의 숫자로 요약해, `is_drift()`가 **RMSE > $4.00이면 드리프트**로 판정할 수 있게 함.

```python
RMSE = sqrt( mean( (actual - predicted) ** 2 ) )
```

**배울 수 있는 것**
- **RMSE의 의미:** 오차를 제곱해 평균 낸 뒤 루트 → 단위가 원래 값(달러)과 같아 "평균적으로 몇 달러 틀리는가"로 해석 가능. 제곱 때문에 **큰 오차에 민감**하다.
- **드리프트는 "입력 분포 변화"를 "성능 저하"로 간접 감지**할 수 있다 (정답 `actual`이 뒤늦게라도 들어오는 경우).
- **윈도우 크기(21)와 임계값($4)은 설계 결정이다:** 짧으면 노이즈에 민감(오탐↑), 길면 반응이 느림. 21 ≈ 한 달 거래일로 절충.
- **경계 조건 처리:** 빈 리스트는 `0.0`(드리프트 없음), 21건 미만이면 판정 보류 → 데이터가 부족할 때 잘못된 경보를 내지 않는다.

## #4 `batch_test()` - 슬라이딩 윈도우 예측 + 기록 누적 (Day3)

**목적**
연속된 가격 배열(41개)을 받아 **20일 윈도우 → 다음날 예측**을 반복하고, `(predicted, actual)` 쌍을 `recent_predictions`에 쌓아 드리프트 판정에 넘김.

```
prices:  [p0 p1 ... p19] p20 → 예측 vs 실제 p20
         [p1 ... p20]    p21 → 예측 vs 실제 p21
         ...  (41 - 20 = 21건)
```

**배울 수 있는 것**
- **시계열 슬라이딩 윈도우:** LSTM 입력이 `(SEQ_LEN=20, 특성 2개)`인 이유, 그리고 윈도우 바로 다음 값이 정답(label)이 되는 구조.
- **왜 41개인가:** `SEQ_LEN(20) + WINDOW_SIZE(21)` → 배치 하나로 정확히 판정 가능한 21건이 생김. 상수 간의 관계를 이해하는 연습.
- **모니터링 버퍼:** 운영 중에는 최근 N건만 유지(`recent_predictions[:] = ...[-WINDOW_SIZE:]`). `[:]` 대입으로 **같은 리스트 객체를 제자리에서 갱신**해 다른 모듈의 참조가 깨지지 않게 함.
- **상수 재사용:** `21`을 하드코딩하지 않고 `drift_detector.WINDOW_SIZE`를 import → 기준이 바뀌어도 한 곳만 수정.
- **테스트 요령:** 가짜 모델(Fake)로 `get_model`을 바꿔치기해 TensorFlow 없이 로직만 빠르게 검증 (`변경.md` #4의 확인 코드).

## #5 `check_and_trigger()` - 드리프트 → 재학습 → 재배포 (Day3)

**목적**
드리프트가 감지되면 로그만 남기던 것을, **최근 1개월 데이터로 fine-tuning → 게이트 검증 → Production 승격 → 서빙 모델 교체**까지 자동으로 이어지게 함.

**배울 수 있는 것**
- **Warm start fine-tuning:** 21거래일로는 LSTM을 처음부터 학습하기엔 샘플이 너무 적다. 이미 3년치로 학습된 Production 가중치에서 **낮은 학습률(1e-4)로 10 epoch만** 이어서 학습 → 안정적이고 빠름.
- **데이터 슬라이싱:** 최근 21일을 예측 대상으로 쓰려면 앞에 20일(SEQ_LEN)이 더 필요 → `[-(21 + SEQ_LEN):]`.
- **배포 게이트:** 재학습했다고 무조건 배포하지 않는다. RMSE ≤ $4를 통과한 경우에만 승격, 아니면 **기존 Production 유지**(안전장치).
- **캐시 무효화(힌트에 없던 버그 수정):** 레지스트리에서 새 버전이 승격돼도 서버 메모리의 `_model_cache`에는 옛 모델이 남아 있다. `model_loader._model_cache = None` 한 줄로 다음 요청에서 새 버전을 로드 → **"레지스트리 갱신 ≠ 서빙 반영"**. 캐시가 있는 곳엔 항상 무효화 시점을 설계해야 한다.
- **지연 import:** `train_and_register`는 import 시 TensorFlow·MLflow를 로드하고 시드를 고정하므로, 드리프트가 실제로 났을 때만 함수 안에서 import → 평상시 요청 비용과 부작용을 줄임.
- **관측 가능성(Observability):** `[WARN] → [INFO] → [OK]` 로그를 `logs/aiops.log`에 남겨, 자동화된 과정이 **실제로 일어났다는 증거**를 사람이 확인할 수 있게 함.

## #6 `send_batch()` - 배치 주입 (Day3)

**목적**
시뮬레이션 스크립트가 만든 정상/드리프트 가격 배치를 `/predict/batch-test`로 전송하고 결과를 출력.

**배울 수 있는 것**
- **API 클라이언트 기본:** `requests.post(json=...)` → `raise_for_status()`로 HTTP 오류를 즉시 예외로 → `resp.json()`. numpy 배열은 `.tolist()`로 JSON 직렬화.
- **드리프트를 재현하는 방법:** 정상/드리프트 모두 **로그수익률 랜덤워크**로 만들고 변동성만 다르게(1.2% vs 3.6%). 평균 주변 백색잡음을 쓰면 추세 있는 시계열을 학습한 모델에겐 "정상" 입력도 이상하게 보여 **오탐**이 난다 → 테스트 데이터도 도메인 특성을 반영해야 한다.
- **실험 설계:** 정상 배치로 베이스라인(RMSE ≤ $4) 확인 → 드리프트 배치로 경보 유발. 대조군이 있어야 감지기가 제대로 동작하는지 말할 수 있다.

## 한 줄 정리

- **Day2:** 모델을 "파일"이 아니라 **레지스트리의 버전**으로 관리하고, 게이트를 통과한 것만 배포한다.
- **Day3:** 운영 중 **예측 오차를 감시**하고, 나빠지면 **자동으로 재학습·검증·재배포**한다 — 그리고 서빙 캐시까지 갱신해야 진짜 반영된다.
