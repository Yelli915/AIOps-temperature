## 1. 배경과 문제 정의

### 1.1 고객의 문제

시설 운영팀은 센서 값으로 서버실 상태를 판단합니다. 그런데 **센서는 고장 납니다.** 값이 0으로 떨어지거나, 갑자기 튀거나, 비어서 들어옵니다.

자동 재학습 파이프라인이 이런 값을 받으면 다음 일이 벌어집니다.

| 고장 유형 | 현재 파이프라인의 동작 | 결과 |
|------|------|------|
| 0 고정, 값 튐 | 엉터리 예측 → 오차 급증 → 드리프트로 판정 → **고장 데이터로 재학습** | 고장 패턴을 배운 모델이 Production이 될 수 있음 |
| 결측 (JSON null, CSV 빈 칸) | null이면 예측 계산 중 `TypeError`로 **500 오류, 로그 없음**. 비표준 NaN 리터럴이면 RMSE가 `nan` → 드리프트 판정이 항상 False → **경보 없이 놓침** → 500 | 문제가 있다는 사실조차 모름 |

결측 경로는 현재 코드로 직접 확인한 결과입니다(`보관/도메인제안.md` 4장).

### 1.2 해결 방향

- **드리프트 판정 전에 데이터부터 검증합니다.** 검증에 실패하면 예측과 재학습을 모두 멈추고 `[SKIP] sensor fault`를 남깁니다.
- **검증을 통과한 상태에서 오차가 커질 때만 진짜 드리프트로 봅니다.** 이때만 재학습 → 게이트 → 재배포로 이어집니다.

### 1.3 예측의 쓰임새

냉방 장애가 나면 과열은 수 분 단위로 진행됩니다. 그래서 1시간 뒤 예측은 **과열 조기 경보용이 아닙니다.**
부하가 몰리는 시간대를 앞두고 **냉방 설정을 미리 조정하고, 작업(부하)을 어느 랙에 배치할지 계획**하는 데 씁니다. 과열 경보는 기존 설비 경보(실시간 임계값)가 맡습니다.

## 2. 목표와 성공 기준

### 2.1 목표

1. HAIC 스켈레톤의 서빙 → MLOps → AIOps 흐름을 서버실 온도 도메인으로 옮긴다.
2. 센서 고장과 진짜 드리프트를 구분하는 **데이터 검증 단계**를 추가한다.
3. 같은 시나리오를 **기존 코드와 새 코드에 각각 돌려** 차이를 수치와 로그로 보여준다.

### 2.2 성공 기준 (완료 체크리스트)

- [x] 192행 미만 CSV는 `/data/upload`에서 거부된다
- [x] 정상 배치는 RMSE ≤ 1.0°C이고 `drift_check.status = "ok"`
- [x] 0 고정 · 값 튐 · 결측 배치 모두 `status = "sensor_fault"`로 응답하고, **예측·재학습이 일어나지 않으며 500 오류가 없다**
- [x] 고장 CSV를 업로드한 뒤에도 재학습이 실행되지 않고 `[SKIP] sensor fault`가 남는다
- [x] 설정온도 상향 · 서버 증설 배치는 `[WARN] → [INFO] → [OK]` 순서로 로그가 남고, 재배포 후 `/predict`가 새 버전으로 응답한다
- [x] 대시보드에 `sensor_fault`가 "정상"이 아니라 고장으로 표시된다
- [x] 시나리오 ①~③의 기존 코드 vs 새 코드 비교표가 있다

|------|------|
| 1시간 뒤 서버실 온도 예측 (LSTM, 기존 구조 재사용) | 냉방기 고장(장애) 대응 - 새로운 정상 상태가 아니라 즉시 대응할 사고. 기존 설비 경보가 맡음 |

## 5. 데이터 설계

### 5.1 CSV 형식

| 컬럼 | 타입 | 설명 |
|------|------|------|
| `Timestamp` | 문자열 | `2026-01-01 00:00` 형식, 1시간 간격 |
| `Temp` | float | 랙 흡기 온도 (°C). 결측은 빈 칸 |
| `LoadKW` | float | IT 전력 부하 (kW) |

- 최소 행 수: **192행** (`SEQ_LEN 24 + RETRAIN_HOURS 168`)
- 샘플 파일: 정상 데이터 약 3개월치(약 2,160행) 권장

### 5.2 가상 데이터 생성 규칙

```
부하 L(t) = L0 × (1 + 0.15 × sin(2π(t − 9) / 24)) + 노이즈        # L0 = 400 kW, 업무 시간대 피크
온도 T(t) = S + a × (L(t) − L0) + 0.3 × sin(2πt / 24) + 노이즈   # S = 설정온도 22°C, a = 0.02 °C/kW, 노이즈 σ = 0.2
```

값은 예시이며 구현하면서 조정합니다. 이 규칙이면 정상 온도는 대략 20~24°C입니다.

| 시나리오 | 생성 방법 |
|------|------|
| ① 정상 | 위 규칙 그대로 |
| ② 0 고정 | 특정 시점부터 N시간 동안 T = 0 |
| ② 값 튐 | 특정 1시간의 T를 ±15°C |
| ② 결측 | 특정 시간의 T를 빈 칸(CSV) / NaN(배치) |
| ③ 설정온도 상향 | 끝나기 72시간 전부터 S = 25°C |
| ③ 서버 증설 | 끝나기 72시간 전부터 L0 = 500 kW |

진짜 드리프트를 72시간 전으로 두는 이유: 변화 후 24시간뿐이면 재학습 데이터의 학습 구간(앞 80%)에 새 상태가 없어 게이트를 통과할 수 없습니다(`변경.md` #27).

## 6. 기능 설계

### 6.1 전체 흐름

```
CSV 업로드 ─▶ /data/upload (192행 이상)
                    │
배치 전송 ──▶ /predict/batch-test
                    │
             ① 입력 검증 ──실패──▶ [SKIP] sensor fault → 예측·재학습 없음 (status: sensor_fault)
                    │ 통과
             ② 슬라이딩 윈도우 예측 → 최근 24건 오차 누적
                    │
             ③ RMSE ≤ 1.0°C ──▶ status: ok
                    │ 초과
             [WARN] drift detected
                    │
             ④ 재학습 데이터(최근 192행) 검증 ──실패──▶ [SKIP] sensor fault → 재학습 차단
                    │ 통과
             [INFO] retrain triggered → fine-tuning(warm start)
                    │
             ⑤ 게이트 RMSE ≤ 1.0°C ──실패──▶ 기존 Production 유지
                    │ 통과
             [OK] production promoted → 모델 캐시 초기화 → 다음 요청부터 새 버전
```

### 6.2 데이터 검증 규칙

서빙 입력(배치·단건)과 재학습 데이터(업로드 CSV)에 **같은 검증 함수**를 씁니다.

| 규칙 이름 | 기준 (조정 가능) | 잡는 고장 |
|------|------|------|
| `missing` | NaN이 1개라도 있으면 실패 | 결측 |
| `out_of_range` | 10°C 미만 또는 40°C 초과 | 0 고정, 값 튐 |
| `stuck_value` | N시간 연속 같은 값 | 0 고정 |
| `sudden_jump` | 인접 1시간 차이 ≥ 10°C | 0 고정 시작 시점, 값 튐 |

범위를 -10~50°C처럼 넓게 두면 0°C가 범위 안이라 0 고정 고장을 통과시킵니다. 서버실 항온 특성에 맞춰 10~40°C로 좁힙니다.

### 6.3 로그 규칙

```
정상:         (로그 없음)
센서 고장:     [SKIP] sensor fault (rule=out_of_range) - prediction & retrain blocked
진짜 드리프트:  [WARN] drift detected → [INFO] retrain triggered → [OK] new_rmse=... - production promoted
```

## 7. API 명세

경로는 HAIC와 같고 필드 이름만 바뀝니다.

### `POST /predict` - 단건 예측

```json
// 요청: 최근 24시간, 오래된 시간 → 최근 시간 순서
{"sequence": [{"temp": 22.1, "load_kw": 410.5}, "... 24개"]}

// 응답 200
{"predicted_temp": 22.43, "model_version": "production"}

// 응답 422 (검증 실패)
{"detail": {"status": "sensor_fault", "rule": "out_of_range"}}
```

- `temp`: float, 음수 허용 (기존 `gt=0` 제거)
- `load_kw`: float, 0 이상

### `POST /predict/batch-test` - 드리프트 시뮬레이션

```json
// 요청: SEQ_LEN(24) + WINDOW_SIZE(24) = 48개 연속 온도
{"temps": [22.0, 22.1, "... 48개"]}

// 응답 - 정상
{"predictions": ["... 24개"], "drift_check": {"status": "ok"}}

// 응답 - 센서 고장 (예측하지 않음)
{"predictions": [], "drift_check": {"status": "sensor_fault", "rule": "missing"}}

// 응답 - 진짜 드리프트
{"predictions": ["... 24개"], "drift_check": {"status": "retrain_triggered", "promoted": true, "rmse": 0.82}}
```

### `POST /data/upload` · `GET /data/status`

| 엔드포인트 | 변경점 |
|------|------|
| `/data/upload` | 필수 컬럼 `Timestamp, Temp, LoadKW`, 최소 192행 |
| `/data/status` | `min_close`/`max_close` → `min_temp`/`max_temp` |

`/health`, `/logs`, `/logs/{파일명}`은 변경 없음.

## 8. 모델·운영 파라미터

| 파라미터 | 값 | HAIC 대비 |
|------|------|------|
| 입력 | 최근 24시간 × (온도, IT 부하) | 20거래일 × (종가, 거래량) |
| 출력 | 1시간 뒤 온도 (°C) | 다음날 종가 ($) |
| 모델 | 3층 LSTM (구조 그대로) | 동일 |
| 드리프트 판정 윈도우 `WINDOW_SIZE` | 24 | 21 |
| 드리프트 임계값 · 배포 게이트 | RMSE 1.0°C (확정: 기준 모델 RMSE 0.22°C의 약 5배) | $4.00 |
| 재학습 데이터 | 최근 168 + 24행 → 학습 134개 / 검증 약 34개 | 41행 → 검증 약 5개 |
| 재학습 방식 | Production 가중치에서 warm start, **20 epoch, 학습률 3e-4** | 10 epoch, 1e-4 (서버실에서는 게이트 미통과 - `변경.md` #27·#28) |
| 스케일러 | 최초 1회 fit 후 고정 | 동일 |

재학습 검증 샘플이 약 5개에서 약 34개로 늘어 게이트 판정이 안정됩니다. 발표에서 언급할 포인트입니다.

## 9. 구현 계획

**순서를 정한 원칙**
1. **의존 순서:** 다른 파일이 import하는 파일부터 바꿉니다. 대부분이 `data/features.py`의 `SEQ_LEN`과 컬럼 이름을 가져다 씁니다.

## 10. 시연 계획 (발표)

| 순서 | 시연 | 보여줄 것 |
|------|------|------|
| 1 | 정상 배치 전송 | `status: ok`, RMSE ≤ 1.0°C |
| 2 | **기존 코드**에 0 고정 배치 | 고장 데이터로 재학습이 실행됨 (`[WARN] → [INFO]`) |
| 3 | **기존 코드**에 결측 배치 | 경보 없이 500 오류 |
| 4 | **새 코드**에 같은 고장 배치 | `[SKIP] sensor fault (rule=...)`, 예측·재학습 없음, 대시보드 고장 표시 |
| 5 | 새 코드에 설정온도 상향 배치 | `[WARN] → [INFO] → [OK]`, `/predict` 새 버전 응답 |
| 6 | 비교표 | 시나리오 ①~③ × 기존/새 코드 |

**핵심 메시지:** "오차가 커진 원인은 모델이 낡았거나 데이터가 망가졌거나 둘 중 하나다. 재학습 전에 데이터부터 의심해야 한다."
